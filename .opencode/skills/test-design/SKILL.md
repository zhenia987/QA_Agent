## Description
Проектирование тестовой модели на основе проанализированных требований. Создание тест-кейсов в **Qase** с привязкой к требованиям и задачам.

## Inputs
- результат этапа **requirements-review** (проанализированные требования, бизнес-правила, ограничения, критерии приемки);
- результат этапа **task-design** (задачи в Jira с ID);
- указание на проект в **TestIt**, в котором должна быть создана тестовая модель;
- правила и место хранения **Artifacts** (структура, формат, идентификаторы этапов).

## Workflow

### 1. Анализ тестового покрытия
- Для каждого функционального требования определить набор тестовых сценариев.
- Для каждого бизнес-правила и ограничения определить сценарии проверки соблюдения.
- Для каждого критерия приемки определить сценарий верификации.

### 2. Проектирование тест-кейсов
- **Название**: отражает проверяемое требование или бизнес-правило.
- **Предусловия**: состояние системы необходимое для выполнения сценария.
- **Шаги**: последовательность действий для проверки.
- **Ожидаемый результат**: конкретное observable поведение системы.
- **Приоритет**: на основе критичности требования.
- **Связь**: указать ID связанных требований и задач.

### 3. Создание тест-кейсов в Qase
- Создать тест-кейсы в указанном проекте Qase.
- Проверить, что тестовое покрытие покрывает все требования.
- Присвоить необходимые атрибуты (теги, приоритеты, разделы).

### 4. Сохранение результата
- Сохранить результат этапа в **Artifacts** с идентификатором этапа.
- Включить: список тест-кейсов с ID, названиями, шагами и связями с требованиями и задачами.

### 5. Проверка качества (Quality Gate)
- тестовые сценарии связаны с требованиями;
- выполнено тестовое покрытие требований;
- присутствуют необходимые атрибуты.

## Outputs
- тестовая модель в **TestIt** (набор тест-кейсов с ID, названиями, шагами, ожидаемыми результатами);
- связь «требование → задача → сценарий»;
- артефакт этапа, сохранённый в **Artifacts** со статусом прохождения **Quality Gate**.

## Constraints
- не создавать тестовые сценарии для поведения системы, которое не описано в требованиях;
- не придумывать требования, бизнес-правила, ограничения, критерии приемки;
- не удалять существующие в Qase сценарии.

## Failure Behaviour
- если **TestIt** недоступен или создание тест-кейса завершилось с ошибкой — остановиться, сообщить пользователю;
- если **Artifacts** недоступны — остановиться и сообщить пользователю;
- если **Quality Gate** не пройден — зафиксировать в артефакте и не помечать этап успешным.
