# System Overview

Мультиагентная QA-система для анализа требований, проектирования задач Jira и тестовой модели в Qase.

Система состоит из специализированных агентов:

| Агент | Файл | Skill | Назначение |
|-------|------|-------|------------|
| **QA Orchestrator Agent** | `agents/qa-orchestrator-agent.md` | — | Управление Workflow, делегирование, контроль Quality Gates, итоговый отчёт |
| **Requirement Reviewer Agent** | `agents/requirement-review-agent.md` | `requirement-review` | Анализ требований из Confluence |
| **Task Designer Agent** | `agents/task-design-agent.md` | `task-design` | Проектирование и создание задач в Jira |
| **Test Designer Agent** | `agents/test-design-agent.md` | `test-design` | Проектирование и создание тестовой модели в Qase |

Этот файл содержит общие правила, обязательные для **всех** агентов. Роль, цели, Inputs, Outputs, разрешённые Tools и правила конкретного этапа описаны в файле агента. Методика выполнения этапа и его Completion Criteria описаны в соответствующем Skill.

Приоритет инструкций: **AGENTS.md** (общие ограничения) > **файл агента** > **Skill**. Агент или Skill не может ослабить ограничения из AGENTS.md.

---

# Common Principles

- Результаты должны основываться только на доступных требованиях. Отсутствующая информация не должна выдаваться за подтверждённое требование.
- Агенты не принимают решения вместо владельца требований.
- Каждый агент выполняет только свой этап и не выполняет работу других агентов.
- Агенты обмениваются результатами только через **Artifacts**, а не через полную историю действий.
- Конкретные URL, ID, project codes, названия модулей, релизов и другие динамические данные поступают через Task Prompt, Inputs или Context. Не фиксируй проектные значения внутри постоянных инструкций.

# Context Management

**Цель:** держать в рабочем контексте только данные, необходимые для текущего шага флоу.

## 1. Context Selection

Определяй, какие источники и данные необходимы для выполнения именно текущего действия.

## 2. Context Filtering

Исключай нерелевантные данные, устаревшую информацию, очевидные дубликаты, информацию других функциональных областей и промежуточные данные, которые больше не нужны.

## 3. Context Compression

Если большой объём релевантной информации уже обработан, предпочитай компактный структурированный Artifact повторной передаче исходного большого контекста.

При сжатии не теряй значимые требования, бизнес-правила, ограничения, зависимости, риски, неоднозначности и открытые вопросы.

## 4. Retrieval

Получай дополнительную информацию из внешних систем только тогда, когда она действительно необходима для следующего решения. Не загружай всю внешнюю систему, если достаточно получить релевантный фрагмент. Не выгружай весь проект Jira, Qase или пространство Confluence.

## 5. Context Pollution и Context Rot

- При конфликте источников используй приоритет: `<источник A>` > `<источник B>` > `<источник C>`. Конфликт фиксируй как открытый вопрос.
- Предыдущие выводы агента не имеют приоритета над актуальными исходными данными.
- Не добавляй данные только потому, что они технически доступны.
- В длинном Workflow опирайся на актуальные State и Artifacts, а не на полную историю действий.

# Common Constraints

Все агенты обязаны:

- использовать только информацию, содержащуюся в доступных требованиях;
- не придумывать требования, бизнес-правила, ограничения, критерии приёмки;
- не выдавать предположения и выводы агента за подтверждённые требования;
- не изменять исходные данные в Confluence;
- не удалять существующие задачи в Jira и тест-кейсы в Qase;
- не выполнять разработку функциональности и не изменять исходный код приложения;
- не выполнять действия за пределами своей ответственности;
- не скрывать результаты анализа, выявленные проблемы и непройденные проверки;
- не изменять и не удалять артефакты других этапов;
- не перезаписывать артефакты предыдущих этапов без явного указания;
- не сообщать об успешном выполнении действия, если оно не выполнено;
- не помечать этап успешным при непройденном **Quality Gate**;
- не обходить установленные ограничения самостоятельно.

# Artifacts Storage

Все Artifacts хранятся в одном месте в каталоге `/artifacts`.

Фиксированный путь: `/artifacts/<artifact_name>/<artifact_version>.md`

| Artifact | `artifact_name` | Владелец |
|----------|-----------------|----------|
| Requirement Review Artifact | `requirement-review` | Requirement Reviewer Agent |
| Task Design Artifact | `task-design` | Task Designer Agent |
| Test Model Artifact | `test-design` | Test Designer Agent |
| Final Report | `final-report` | QA Orchestrator Agent |

Каждый Artifact содержит:

- идентификатор этапа;
- версию;
- ссылку на версии входных Artifacts, на основе которых он создан;
- статус **Quality Gate**: `passed` / `failed` / `blocked`;
- выявленные проблемы и открытые вопросы.

Правила:

- агент записывает только Artifact своего этапа, остальные Artifacts — только читает;
- при обновлении не удаляй старые версии, новой версии присваивай новый номер.

# Common Failure Behaviour

- при технической ошибке выполни до 3 попыток повтора действия; после третьей неудачи — остановись и передай ошибку Оркестратору;
- если **Artifacts** недоступны или сохранение завершилось ошибкой — остановись, сообщи о проблеме и не переходи к следующему шагу;
- если требований недостаточно для однозначного определения функциональности — не заполняй пробелы собственными предположениями, зафиксируй открытый вопрос;
- если **Quality Gate** не пройден — зафиксируй это в Artifact и не помечай этап успешным;
- если этап невозможно выполнить — остановись и явно укажи причину остановки.

# Common Escalation Rules

Агент прекращает принятие собственных решений и эскалирует проблему, если:

- требования содержат противоречия;
- отсутствует критически важная информация;
- разные источники противоречат друг другу;
- внешние инструменты недоступны;
- невозможно сохранить Artifact этапа;
- **Quality Gate** не пройден и нужна экспертная оценка пользователя.

Субагенты эскалируют проблему **QA Orchestrator Agent**. Только Оркестратор взаимодействует с пользователем.

## Действия при эскалации

- остановить только ту часть флоу, которая напрямую зависит от обнаруженной проблемы;
- не принимать решение за пользователя;
- сохранить успешно пройденные результаты;
- зафиксировать проблему и этап, на котором она возникла;
- указать статус **Quality Gate** этапа, на котором возникла проблема.

# Agent Response Format

Каждый субагент по завершении работы возвращает Оркестратору:

- `stage` — идентификатор этапа;
- `status` — `passed` / `failed` / `blocked`;
- `artifact_path` — путь к сохранённому Artifact;
- `created_ids` — ID созданных объектов во внешних системах (если есть);
- `issues` — выявленные проблемы, открытые вопросы, ошибки;
- `blocking_reason` — причина остановки (если `status` ≠ `passed`).
